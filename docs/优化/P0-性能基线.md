# P0：性能基线

## 本阶段目标

P0 将原本写死在 `bench.py` 中的工作负载和引擎配置改为命令行参数，并增加分阶段性能指标，使不同优化可以在相同模型、序列长度、并发规模和执行模式下重复测试。目前已完成参数化和指标采集两部分。

## 第一阶段：工作负载参数化

`bench.py` 现在支持以下配置：

- `--model`：本地模型目录；
- `--num-prompts`：整次测试提交的请求总数；
- `--max-num-seqs`：调度器单批允许的最大并发序列数；
- `--input-len`、`--output-len`：固定输入和输出长度；
- `--min-input-len`、`--max-input-len`：随机输入长度范围；
- `--min-output-len`、`--max-output-len`：随机输出长度范围；
- `--max-model-len`、`--max-num-batched-tokens`：模型上下文上限和单次 Prefill token budget；
- `--tensor-parallel-size`：Tensor Parallel 使用的 GPU 数量；
- `--gpu-memory-utilization`：KV Cache 可使用的显存比例；
- `--enforce-eager`：关闭 Decode CUDA Graph，改用 Eager 模式；
- `--temperature`、`--seed`：采样温度和工作负载随机种子。
- `--warmup-runs`：正式计时前执行的短请求次数，默认 1；
- `--output-json`：将本次配置和指标写入 JSON 文件。

固定长度参数会覆盖对应的随机长度范围。不指定固定长度时，默认保持原有行为：输入和输出长度分别在 100～1024 之间随机生成。随机 token ID 改为按照当前模型的真实词表大小生成。

## 使用示例

固定长度 CUDA Graph 基线：

```bash
python bench.py \
  --model ~/huggingface/Qwen3-0.6B \
  --num-prompts 256 \
  --max-num-seqs 64 \
  --input-len 1024 \
  --output-len 128
```

Eager 对照组：

```bash
python bench.py \
  --model ~/huggingface/Qwen3-0.6B \
  --input-len 1024 \
  --output-len 128 \
  --enforce-eager
```

双卡 Tensor Parallel：

```bash
CUDA_VISIBLE_DEVICES=0,1 python bench.py \
  --model ~/huggingface/Qwen3-0.6B \
  --tensor-parallel-size 2 \
  --max-num-seqs 64
```

保存机器可读结果：

```bash
python bench.py \
  --model ~/huggingface/Qwen3-0.6B \
  --num-prompts 256 \
  --max-num-seqs 64 \
  --input-len 1024 \
  --output-len 128 \
  --output-json benchmarks/qwen3-0.6b-bs64-in1024-out128.json
```

## 参数校验

脚本会拒绝非正数的长度、请求数量和 TP 数量，并检查：

```text
min_input_len <= max_input_len
min_output_len <= max_output_len
max_input_len + max_output_len <= max_model_len
0 < gpu_memory_utilization < 1
temperature > 1e-10
warmup_runs >= 0
```

需要注意，`num-prompts` 表示总请求数，`max-num-seqs` 表示调度并发上限，两者不是同一个 batch size。CUDA Graph 当前只覆盖 Decode，并且 graph batch bucket 最大为 512；更大的 Decode batch 会回退到 Eager 路径。

## 第二阶段：分阶段指标采集

`LLMEngine` 新增了向后兼容的观测接口：

- `add_request()` 返回新请求的 `seq_id`，旧调用方可以忽略返回值；
- `step_with_info()` 返回本轮输出和 `StepInfo`；
- 原有 `step()` 和 `generate()` 的参数及返回形式保持不变；
- `Scheduler.postprocess()` 返回本轮真正生成 token 的序列 ID。未完成的 Chunked Prefill 不会被误判为首 token。

`StepInfo` 包含执行阶段、调度 token 数、序列数、本轮生成 token 的请求以及完成的请求。Benchmark 在每个 step 边界执行 CUDA 同步并统计：

| 指标 | 计算方式 |
|---|---|
| E2E Throughput | 总输出 token / 全部请求完成时间 |
| Prefill Throughput | 实际调度的 Prefill token / Prefill step 总时间 |
| Decode Throughput | Decode 阶段生成 token / Decode step 总时间 |
| TTFT | 统一计时起点到该请求生成首 token 的时间 |
| TPOT | 首 token 到请求完成的时间 / 后续 token 数 |
| P50/P95/P99 | 所有请求 TTFT 或 TPOT 的线性插值分位数 |
| Peak Memory | 重置峰值统计后 rank 0 的最大 allocated memory |

TTFT 包含请求在调度队列中的等待时间。首 token 在完成 Prefill 的 step 中产生，因此不会计入 Decode Throughput。若所有请求只输出一个 token，则不存在 Decode step 和 TPOT，JSON 中对应值为 `null`，终端显示 `n/a`。

JSON 报告包含完整 benchmark 配置、GPU 名称、总输入/输出 token、Prefill/Decode token 与 step 数、各阶段耗时、吞吐、延迟分位数和峰值显存。当前多卡模式的显存指标仅代表 rank 0，不能视为所有 GPU 的显存总和。
