# P3：输入缓冲与异步执行

## 当前状态（2026-10-03）

已完成 P3.1 的 Decode 持久化缓冲、显式执行开关、计时模式、分段 profiling、正确性验证和50次端到端对照。默认仍为 `original`。

CPU 测试、单卡真实模型 Eager/CUDA Graph 对照，以及 TP=2 buffered 冒烟已通过。释放 GPU1 后完成三次关卡采集，可提前准备的元数据时间约占步骤时间的2%，未达到约定的5%。**按条件式推进方案，本轮交付 P3.1，不实施 P3.2。** 首轮实现时其他任务占用 GPU，相关检查只用于正确性，未用于性能结论。

## 实现与边界

- `nanovllm/engine/decode_buffers.py`：持久化 pinned CPU/GPU 缓冲，CPU 通过 NumPy 视图填充。token/position 合为一块 int64 存储，slot/context length 合为一块 int32 存储。
- block table 保存不可变快照，行顺序、序列身份或内容变化时更新；温度未变化时跳过搬运。稳定 Decode 通常只有两次输入 H2D；批次变化时另传 table/temperature。全容量小向量传输可能比原路径传输更多字节，因此必须同时看次数和字节数。
- CUDA Graph 直接引用持久化输入，省去临时输入到 Graph 输入的重复 D2D 拷贝。补全1/3/7/17等非标准并发上限对应的桶，不进行额外桶调优。
- 每次覆盖 pinned host 数据前等待上一轮 H2D 完成事件；同一 stream 保证设备端输入更新发生在此前计算结束之后。各 TP rank 分别维护缓冲，只有 rank0 保存采样温度。
- 新缓冲在 KV Cache 分配前创建，纳入可用显存预算；Graph 地址固定。Prefill 沿用原准备逻辑，跨 block、批次变化和尾部 padding 均由下一次 Decode 更新处理。

这里的 `buffered` 仍然同步返回采样结果，**不代表已经实现 CPU/GPU 流水线重叠**。普通 EOS 请求继续使用原有结束逻辑。

## 使用与计时

```bash
CUDA_VISIBLE_DEVICES=1 python bench.py \
  --execution-mode buffered --measurement-mode runtime \
  --max-num-seqs 64 --input-len 128 --output-len 512 \
  --warmup-decode-steps 32 \
  --output-json benchmarks/results/p3-runner-gpu1/manual/decode-1.json
```

- `--execution-mode original|buffered`：默认 `original`；库接口使用 `LLM(..., execution_mode="buffered")`。当前没有 `async` 选项，传入会明确报错。
- `--measurement-mode sync|runtime`：默认保留逐步全设备同步；`runtime` 只在整轮边界显式同步，步骤本身仍等待真实采样结果返回 CPU。当前两种执行路径的阶段时间均为已完成步骤的墙钟时间，不是纯 kernel 时间。
- `--warmup-decode-steps 32`：以相同最大并发预热32个 Decode 步骤；随后清除预热产生的 Prefix Cache 索引，避免测量请求直接复用预热前缀。测量前重置采样种子。
- JSON 记录执行/计时模式、GPU UUID、PyTorch/CUDA 版本、KV block 数、缓冲字节数，以及代码提交号和工作区是否有修改。旧结果保留，不与不同计时口径直接混算。

GPU1 空闲后运行完整对照：

```bash
CUDA_VISIBLE_DEVICES=1 bash benchmarks/scripts/run_p3_runner.sh
```

主对照固定 `RMSNorm=compiled`、P2关闭；三组固定负载各运行 original/buffered 五次，每次轮换顺序。再打开P2，对 decode-heavy、balanced 各做五次叠加对照。共50次独立进程运行。每轮均进行代表性预热，输出中位数对比和均值/标准差。目录为 `benchmarks/results/p3-runner-gpu1/p2-{0,1}/{original,buffered}/`。

脚本支持 `PYTHON_BIN`、`MODEL_PATH`、`RESULT_ROOT`、`RUNS`；原固定负载脚本增加 `EXECUTION_MODE`、`MEASUREMENT_MODE`、`WARMUP_DECODE_STEPS`、`RUN_START`。正式验收保留 `RUNS=5`。

## 端到端结果

环境：GPU1 RTX 3090、Qwen3-0.6B、TP=1、CUDA Graph、RMSNorm compiled、PyTorch `2.13.0+cu130`、CUDA 13.0。测量代码为 `3cdd48a` 加本次尚未提交的P3修改；测量期间未改执行代码。每次运行预热32个Decode步骤，`measurement_mode=runtime`、seed=0。同一组十份JSON中，除 `execution_mode` 外配置全部一致，KV Cache均为703个block。

观察与限制：

- 25组配对E2E结果均为正向。P2关闭的decode-heavy范围为7417.60～7586.85 vs 7569.72～7649.49 tok/s，仍有重叠；balanced范围为2532.02～2542.78 vs 2555.88～2558.46 tok/s。
- Prefill-heavy收益只有0.15%，Prefill吞吐及部分TTFT还略有回退，不应宣传为显著改善。TPOT百分位来自每个请求的平均token间隔，不是逐token ITL的百分位。
- GPU1抽查时只有本次测试进程；GPU2在后续运行中出现其他用户任务，CPU等主机资源并未完全隔离。没有锁定GPU时钟，结果只代表本机本配置的这组重复实验。
- P2关/开是两组独立的P3 A/B实验，分别交替original/buffered；不能跨两组相减来归因P2收益，也不能将两个阶段的百分比直接相加。
- 本次使用runtime计时和代表性预热，不能与旧P2文档的历史baseline直接相减。峰值显存按MiB显示与original一致；这里只能声称避免重复输入分配，不能声称显著节省整机显存。

## Profiling 与异步关卡

```bash
CUDA_VISIBLE_DEVICES=1 EXECUTION_MODE=buffered PROFILE_STAGES=1 \
  PROFILE_DIR=benchmarks/profiles/p3-runner-gpu1/buffered \
  bash benchmarks/scripts/profile_torch.sh decode

CUDA_VISIBLE_DEVICES=1 bash benchmarks/scripts/profile_p3_runner.sh
```

分段范围包括 `schedule`、`prepare_inputs`、`host_buffer_wait`、`decode_metadata`、`h2d`、`model`、`sample`、`d2h` 和 `postprocess`，统一使用 `nanovllm::` 前缀。默认关闭详细标记；性能对照不使用 profiler。`model` 包含模型前向和 LM head，`sample` 是采样提交，`d2h` 包含等待结果，不能把这几个 CPU 范围当作 GPU 执行时长。

关卡脚本固定 B=64、输入128、TP=1、P2关闭、CUDA Graph，独立捕获三次105步，丢弃每次前5步。`analyze_runner.py` 从 Nsight SQLite 读取 NVTX 和实际 GPU node 活动，合并重叠区间，避免重复累加 CUDA 时间；校验三组配置一致并生成 `benchmarks/profiles/p3-runner-gpu1/gate.json`。

每步取 `min(Decode 元数据 CPU 时间, GPU 空闲时间) / 步骤墙钟时间` 作为可重叠空间的估计。至少两次采集的中位数达到5%，且可隐藏时间的运行间中位数大于两倍 MAD，才进入 P3.2。该估计包含 profiling 开销，代表尝试空间，不是预期提速。H2D、采样等待和依赖结果的后处理不直接计作可提前执行的 CPU 工作。

**只有 GPU 空闲、三次配置一致且正确性通过时，关卡结果才有效。缺少测量表示待验收，不等于关卡失败。** 不使用“GPU 被别的进程占用”造成的空隙决定是否实现异步。分析脚本仅输出判定，不会自动修改代码。

本次使用物理 GPU1（RTX 3090，UUID `GPU-e9e4afed-ebf4-e4ec-28e4-598dada14eac`），开始前 GPU1/GPU2 均只有15 MiB占用、0%利用率；采集期间 GPU1 没有其他计算进程。每次保留100步：

| 采集 | 步骤中位数 / µs | GPU空闲中位数 / µs | 元数据中位数 / µs | 可重叠比例中位数 |
| --- | ---: | ---: | ---: | ---: |
| 1 | 7438.67 | 1889.52 | 149.57 | 2.01% |
| 2 | 7341.70 | 1791.18 | 148.12 | 2.03% |
| 3 | 7243.87 | 1726.93 | 141.40 | 1.95% |

三次均未达到5%；可隐藏时间的运行间中位数148.12 µs，MAD为1.45 µs。**未通过的是收益空间门槛，不是正确性测试。** GPU空闲也包含提交、同步等开销，不能全部算作下一步元数据准备能消除的时间。此结论仅适用于当前模型、B=64和所定义的保守关卡，不说明其他负载下异步无价值。

每次105步的 persistent-input H2D计数为211次、165376字节：每步两次小向量搬运，加首次 block table 上传。缓冲在CPU/GPU各占5888字节。保留窗口中有43200次kernel活动和400次memcpy活动；后者包括输入以外的传输，不能当作H2D调用数。

补测同配置original路径，并对两条路径分别运行20步Torch profiler。Nsight均丢弃前5步、保留100步；Torch只统计后15步的CPU `prepare_inputs` 范围：

| 稳定Decode每步指标 | Original | Buffered |
| --- | ---: | ---: |
| H2D调用数 | 6 | 2 |
| H2D字节数 | 2048 | 1536 |
| D2D memcpy活动数 | 5 | 1 |
| kernel活动数 | 435 | 432 |
| 输入准备内 `aten::empty` 调用数 | 6 | 0 |
| 输入准备内 `aten::empty_strided` 调用数 | 6 | 0 |

H2D调用减少66.7%，本配置下H2D字节减少25%；不是所有形状都会减少字节数。`aten::empty*` 是张量存储分配请求，不代表每次都调用物理 `cudaMalloc`；Torch缓存分配器会复用内存。

Nsight中original输入准备CPU范围中位数580.57 µs；buffered三次为617.58、537.52、517.07 µs，既有波动，也包含更细的嵌套标记开销，因此不据此宣称稳定的CPU耗时下降比例。100步kernel累计时间original为554.01 ms，buffered为555.64～556.94 ms，基本未变；该改动的收益来自输入准备/提交和拷贝开销，不是模型计算加速。
