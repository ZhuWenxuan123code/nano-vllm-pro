# P5：在线混合调度与自适应 Prefill 预算

## 验收结论

完整 282 次实验及结果审计已结束：12 次标定、60 次预算扫描、180 次主对照和 30 次组合对照。42 个正式策略/负载档位均完成五轮，默认仍为 legacy。

固定 mixed 有负载特定价值：稳定到达 0.9 档总体吞吐中位数提高 16.09%；长短混合 0.9 档 ITL P99 下降 87.19%，但伴随 TTFT 上升和吞吐回退。高档 KV 压力和组合实验没有综合 SLO 收益，自适应控制器多数配置明显退化。**实现、正确性兼容和实验闭环已完成，不代表取得了普适提速或达到了所有 SLO；adaptive 不建议启用为默认。**

## 边界与开关

默认仍使用 `scheduler_policy=legacy`。`mixed` 优先运行 Decode，再用剩余 token/序列预算加入 Prefill chunk；`adaptive` 根据 CPU 可见 ITL 调整预算。首版不是异步流水线，也不提供 HTTP 服务。

混合 batch 按 Decode、Prefill 排列，一次模型前向共享 QKV/MLP GEMM，Attention 分段读取分页缓存。只写一次 KV。混合 batch 走 Eager、禁用 P2；纯 Decode 继续使用 CUDA Graph、P2 和 P3 缓冲复用。中间 Prefill chunk 的采样结果被丢弃，不产生正式 token 事件。

主要接口：

| 参数 | 默认值 | 含义 |
| --- | --- | --- |
| `scheduler_policy` | `legacy` | `legacy` / `mixed` / `adaptive` |
| `prefill_token_budget` | 256 | 有 Decode 时的固定预算/自适应初值 |
| `prefill_budget_min/max` | 64 / 1024 | 自适应预算范围；64 token 粒度 |
| `ttft_slo_ms/itl_slo_ms` | 2000 / 50 | 实验延迟目标，不是生产服务承诺 |
| `prefill_max_wait_ms` | 1000 | 资源允许时的等待保护阈值 |
| `kv_cache_block_limit` | 引擎默认不限制 | 显式锁定 KV block 数，内存不足报错 |

`bench.py` 支持调度策略、固定预算和缓存上限；在线工具支持全部参数。`StepInfo.phase` 区分 `prefill/decode/mixed`，分别记录 token 数、预算、执行路径和 KV 占用。旧 `is_prefill` 在 mixed 下只表示“包含 Prefill”；不能用它推断独占阶段或拆分时间。

## 控制与资源管理

自适应反馈来自 step 返回后可见 token 的间隔，不来自 GPU 提交耗时。EMA 系数 0.2：实际 ITL 超过目标立即减半；每 4 个 Decode-bearing step 检查一次，EMA 达到目标 90% 时减半。连续两个窗口低于目标 75%、有等待请求且 KV 占用低于 85% 时增加 64 token。没有 Decode 时使用完整全局 token budget。

KV 占用达到 90% 时暂停新准入，但继续推进已驻留的部分 Prefill。保留完整 prompt 分配方式，没有把本阶段收益混入按 chunk 分配的缓存改造。驻留请求数有上限，准入为下一步 Decode 扩页保留空间；只抢占本批尚未选中的请求，统计实际重复执行的 token。

Prefill 按驻留优先、最近服务时间排序；预算下限保证资源允许时的最小服务机会，超过等待阈值记录保护服务。Decode 占满名额或 KV 不足时，不强行暂停 Decode，也不承诺硬等待上限。

## 在线计时与正确性口径

预生成到达轨迹及 prompt seeds，记录实际 token 哈希和轨迹哈希。执行期间到达的请求在 step 返回后补交；TTFT 始终从计划到达计时，额外报告提交延迟。逐 token 时间取采样回到 CPU 后的 step 返回时间；不逐步增加全设备同步。

`queue_wait_ms` 为计划到达至第一次调度，包含 `submission_lag_ms`（计划到达至实际提交）；二者不能相加。实际提交后的引擎排队时间可从原始 `submitted_s/first_scheduled_s` 相减得到。

ITL 是同一请求相邻 token 的时间差，不是平均 TPOT。完成请求仅在 TTFT≤2000 ms 且**全部 ITL≤50 ms**时计入有效 req/s 和有效 output tok/s。单 token 请求仅检查 TTFT。吞吐分母包含请求到达间隙和最终 drain；超时试验保存未完成请求并明确失败，不能从分母删除。混合时间独立记账，不重复归入 Prefill/Decode。

正确性分两层：

- 固定 Q/K/V、分页数据及 chunk 边界，混合 Attention 与原分段路径在 FP16/BF16、Flash/Triton 高精度/INT8 下逐位一致。
- 模型级 teacher forcing 固定 GEMM 形状、chunk、Graph/P2/P3 开关，对照原 Attention 分段调用，检查 logits、缓存、前缀复用及最终释放；另验证 TP=2。

初始跨策略对照曾失败：不同 chunk 边界会改变 INT8 第一段连续高精度 Attention 与后续量化缓存 Attention 的使用范围；将模型拆成两次前向也会改变 BF16 GEMM 舍入。后续隔离这些变量，未通过放宽容差掩盖差异。本阶段 INT8 验证是实现兼容性，**不能把 P4 的固定子集困惑度门槛自动推广到任意新调度/chunk 配置**。

结论与边界：

- 固定 mixed 在稳定到达的三档总体吞吐分别提高 9.43%/16.09%/15.67%；0.9 档抢占中位数由 32 次降至 0，重计算比例由 11.11% 降至 0。但 TTFT P99 从 83.07 ms 增至 2558.26 ms，不能称为全面降低延迟。
- 突发负载总体吞吐回退 3.77%～19.24%；0.9 档有效吞吐由 0 增至 1493.28 tok/s，同时 SLO miss 仍有 53.52%。基线为零时只报告绝对改善，不计算无限百分比。
- 长短混合 0.9 档 ITL P99 从 623.00 ms 降至 79.79 ms（下降 87.19%），但仍高于 50 ms 目标；总体吞吐回退 2.73%，TTFT P99 上升 17.57%。有效吞吐 56.55→74.41 tok/s 的样本标准差分别为 0.21/31.38，不能据此宣称稳定的 31.59% 有效吞吐提升。
- adaptive 在上述九档总体吞吐全部回退，幅度约 81.88%～91.04%，应作为当前控制器的负结果交付，而不是启用为默认或写成简历提速。

**为什么 legacy 的 ITL P99 很小，有效吞吐却为零？** ITL P99 聚合所有 token 间隔；每请求 128 个输出对应 127 个间隔，即使每个请求都有一个严重停顿，占比也只有约 0.79%，P99 可能看不到。steady/burst 的 0.9 档 legacy 每请求最大 ITL 的 P50 分别约 7051/1372 ms，不能只据 16.31/11.08 ms 的 token ITL P99 判断请求达标。

**adaptive 为什么退化？** 正式运行中 mixed 的 CPU 可见间隔接近 45 ms，已接近 50 ms 目标的 90% 降预算线；短时超标会减半，又很难达到 37.5 ms 的增预算条件。0.9 档 steady 的 mixed step/64-budget step 中位数为 2024/2016，长短混合为 6608/6559；大量小 chunk 把时间消耗在 Eager launch 与排队上。突发组也存在预算停在 256 的运行，故不是每次都收缩到 64。当前正式矩阵保持原控制器不变，不能边看结果边修改阈值。

有效吞吐波动明显：steady/burst 0.9 档固定 mixed 的 std 分别为 1044.02/818.68 tok/s，而总体吞吐 std 仅为 29.04/121.40 tok/s。一次超标间隔可令同一批多个请求失去“全部 ITL 达标”的资格；报告必须保留这种敏感性，不能只取最好一轮。九种宽松/严格 SLO 的后处理数据在原始 JSON 的 `slo_sensitivity` 中，不能更换验收阈值掩盖失败。

结果是调度、驻留数量上限和 KV 准入保护的组合效果；尚未做“仅准入限制、不混合”的独立消融，所以不能把吞吐收益全部归因于共享 GEMM。合成随机 token 不代表真实文本服务，也不能直接套用到其他 GPU/模型或在线 HTTP 服务。

全结果审计 `audit-final.json` 校验全部 282 次的源代码/测量哈希、GPU1 UUID、软件版本、容量、每请求 128 个输出事件和最终缓存归还；重新生成计划到达轨迹与输入 token 哈希，并从原始 token 时间核算逐请求 SLO。正式结果没有超时或编译回退日志。不要求不同调度的随机生成 token 内容逐个相同；历史 `audit-snapshot.json` 只作为运行中检查点保留。

### 独立 Nsight 诊断

三条冻结 16 请求轨迹均完成，结果位于 `benchmarks/profiles/p5-scheduling-gpu1/`。Graph node 记录包含图内节点，kernel 次数不是 Graph replay 次数。

| 策略 | Prefill/Mixed/Decode steps | 全部 kernel 次数 | 图内 kernel 次数 | 累计 kernel CUDA ms | 活跃 step 内 GPU 无活动比例 |
| --- | --- | ---: | ---: | ---: | ---: |
| legacy | 16 / 0 / 127 | 64865 | 57150 | 731.94 | 53.21% |
| mixed（预算 256） | 1 / 30 / 127 | 72956 | 57038 | 866.54 | 64.67% |
| adaptive | 1 / 116 / 127 | 119544 | 56702 | 1226.04 | 82.77% |

“活跃 step”由 NVTX schedule 开始至对应 postprocess 结束定义，GPU 活动取 kernel/memcpy/memset 区间并集；排除 step 之间的到达等待，不累加重叠区间。累计 CUDA 时间是 kernel 时长之和，不是墙钟时间，也不是硬件利用率。

混合模型的 CPU NVTX 区间中位数约 52.93/53.09 ms，观察到大量 host launch 间隙；纯模型区间多数为 Graph 提交，约 1.05 ms，**不是完整 GPU 前向完成延迟**。这些记录支持混合 Eager 是重要成本的判断，但不能将 profiler 下的延迟或有效吞吐写入无 profiler 性能表。Profiler 还可能改变自适应控制的反馈和预算轨迹。
