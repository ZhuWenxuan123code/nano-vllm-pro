# Nano-vLLM 优化路线

## 目标与原则

本项目的差异化不应只是“复现 vLLM”，而应体现三类能力：能够用 Profiler 找到瓶颈、能够编写并验证 GPU 算子、能够从端到端指标说明优化价值。每项优化都必须保留正确性测试、独立 microbenchmark 和端到端结果，避免只报告单个 kernel 的加速比。

建议以 RTX 3090 上的 Qwen3-0.6B 为固定基线，同时区分 Prefill 与 Decode，记录吞吐、TTFT（首 token 延迟）、TPOT（每输出 token 时间）、P50/P99 延迟、峰值显存和 kernel 数量。

## P0：先建立可信的性能基线

这是后续所有优化的前提，优先级最高，但不作为最终亮点。

- 扩展 `bench.py`，支持 batch size、输入/输出长度、eager/CUDA Graph、TP 卡数等参数。
- 使用 `torch.profiler` 和 Nsight Systems 分别分析 Prefill、Decode，输出 CUDA 时间占比和 kernel launch 次数。
- 使用 Hugging Face 输出作为正确性参考，比较 token 或 logits；固定随机种子并完成 warmup。
- 将结果保存为 JSON/CSV，并生成优化前后的对比表。

验收标准：同一配置重复运行误差稳定，所有后续 PR 都能通过一条命令与 baseline 比较。

## P1：融合 Add + RMSNorm 算子

当前 `RMSNorm.add_rms_forward` 完成残差相加、FP32 方差计算、归一化和权重缩放，并依赖 `torch.compile` 融合。可先实现 Triton 版本，再视需要编写 CUDA C++ 版本。

实现内容：

- 支持 FP16/BF16 输入、FP32 累加以及普通 RMSNorm 和 Add-RMSNorm 两种路径；
- 一次读取 `x` 与 `residual`，同时输出归一化结果和新 residual；
- 针对常见 hidden size 调整 `BLOCK_SIZE`、warps 和向量化加载；
- 与 PyTorch、`torch.compile` 对比数值误差及不同 token 数下的延迟。

推荐原因：实现边界清晰，每个 Decoder Layer 调用两次，适合作为第一个完整算子项目。若端到端收益有限，也应如实分析其受 GEMM 占比限制的原因。

## P2：融合 Q/K Norm + RoPE + KV Cache 写入

这是最推荐的核心亮点。当前 Attention 路径依次执行 Q/K RMSNorm、RoPE 和独立的 KV Cache 写入，Decode 时 batch 较小，容易受到显存访问和 kernel launch 开销影响。

实现内容：

- 为 Decode 编写融合 kernel：读取 Q/K/V，完成 Q/K RMSNorm、RoPE，并按照 `slot_mapping` 将 K/V 写入 Paged KV Cache；
- Q 写入连续输出供 FlashAttention 使用，K/V 直接写 cache；
- 为 Prefill 保留原路径，或单独实现能同时输出连续 K/V 和写 cache 的版本；
- 支持 GQA、不同 head dimension、无效 slot（`-1`）和 CUDA Graph 固定地址。

验收时分别报告融合前后的 kernel 数、显存读写量估算、单层延迟、Decode TPOT 和端到端吞吐。该工作同时展示 Transformer 结构、Paged KV Cache、Triton/CUDA 和推理阶段差异，最适合写入简历。

## P3：融合采样并减少全词表开销

当前 `Sampler` 会生成完整 softmax 概率和同尺寸随机张量。可实现 temperature + top-k + sampling 融合 kernel，使用分块归约，只保留候选 token，避免物化完整概率张量。

进一步可优化 Tensor Parallel：`ParallelLMHead` 当前把各 rank 的完整 logits gather 到 rank 0。对于 top-k sampling，可让每个 rank 先计算局部 top-k，再只通信候选值和全局 token id，最后在 rank 0 合并与采样。

验收指标包括 vocab size、batch size、k 值变化下的采样延迟、临时显存和 TP 通信量。必须验证 greedy、temperature 和 top-k 的边界行为；随机采样应验证分布，而不只比较单次 token。

## P4：调度与推理系统优化

在完成一个算子亮点后，再增加一个系统级亮点：

- **自适应 Chunked Prefill**：根据 Decode batch、token budget 和等待时间动态决定 prefill chunk，降低长请求对短请求 TTFT/TPOT 的干扰。
- **Prefix Cache 指标与淘汰策略**：统计命中 token、节省的 prefill 计算和复用次数；由简单空闲队列改为基于 LRU/收益的淘汰策略。
- **CUDA Graph bucket 优化**：根据真实 batch 分布选择 graph bucket，减少 padding 计算和 graph 占用显存。

系统优化应使用混合工作负载测试，而不是只测固定长度离线吞吐。建议构造短对话、长 prompt 和并发 decode 混合场景，报告 TTFT、TPOT、P99 和有效 token 吞吐。

## P5：高难度扩展项

以下项目价值高，但不建议在前面工作完成前启动：

- 实现 INT8/INT4 weight-only Linear，包括权重打包、量化加载和 Tensor Core GEMM；
- 实现 Speculative Decoding，并处理 draft/target KV Cache 的提交与回滚；
- 实现不依赖 FlashAttention 的 Paged Decode Attention，用于展示完整的在线 softmax、分块 KV 读取与归约设计。

直接重写普通 FP16 GEMM 或完整 FlashAttention 风险很高，通常难以超过 cuBLAS/FlashAttention，也不容易形成可信成果。

## 推荐实施顺序

1. 第 1 周：建立 benchmark、正确性测试和 profiler 报告。
2. 第 2 周：实现 Add + RMSNorm，形成第一份算子优化报告。
3. 第 3～5 周：实现 Decode 的 Q/K Norm + RoPE + KV Cache 融合。
4. 第 6～7 周：实现 fused top-k sampling；有多卡时继续优化 TP logits 通信。
5. 第 8 周以后：选择自适应 Chunked Prefill 或 Speculative Decoding 作为系统扩展。

时间有限时，完成 **P0 + P1 + P2** 即可形成一条完整故事线；不要同时铺开多个只有接口、没有测试和数据的功能。

## 简历呈现方式

不要写“基于 nano-vLLM 实现推理框架”，而要突出问题、方法和量化结果。例如：

> 基于 Triton/CUDA 为 Qwen3 推理链路实现融合 Q/K RMSNorm、RoPE 与 Paged KV Cache 写入算子，将 Decode kernel 数由 X 降至 Y，单层延迟降低 X%，端到端 TPOT 降低 Y%；设计 FP32 累加与多种 head dimension 的正确性测试，并通过 Nsight 分析显存访问和 launch 开销。

最终 README 应包含架构图、复现命令、硬件与软件环境、baseline、消融实验和局限性。真实且可复现的 5% 端到端提升，比无法解释来源的数倍 kernel 加速更有说服力。
