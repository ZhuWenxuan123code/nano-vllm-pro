# Nano-vLLM 优化路线

## 目标与原则

本项目的差异化不应只是“复现 vLLM”，而应体现三类能力：能够用 Profiler 找到瓶颈、能够编写并验证 GPU 算子、能够从端到端指标说明优化价值。每项优化都必须保留正确性测试、独立 microbenchmark 和端到端结果，避免只报告单个 kernel 的加速比。

建议以 RTX 3090 上的 Qwen3-0.6B 为固定基线，同时区分 Prefill 与 Decode，记录吞吐、TTFT（首 token 延迟）、TPOT（每输出 token 时间）、P50/P99 延迟、峰值显存和 kernel 数量。

## P0：先建立可信的性能基线

这是后续所有优化的前提，优先级最高，但不作为最终亮点。

- 扩展 `bench.py`，支持 batch size、输入/输出长度、eager/CUDA Graph、TP 卡数等参数。（已实现）
- 使用 `torch.profiler` 和 Nsight Systems 分别分析 Prefill、Decode，输出 CUDA 时间占比和 kernel launch 次数。（已完成）
- 使用 Hugging Face 输出作为正确性参考，比较 token 或 logits；固定随机种子并完成 warmup。 (暂不实现)
- 将结果保存为 JSON/CSV，并生成优化前后的对比表。（已实现）

验收标准：同一配置重复运行误差稳定，所有后续 PR 都能通过一条命令与 baseline 比较。

## P1：融合 Add + RMSNorm 算子

当前 `RMSNorm.add_rms_forward` 完成残差相加、FP32 方差计算、归一化和权重缩放，并依赖 `torch.compile` 融合。可先实现 Triton 版本，再视需要编写 CUDA C++ 版本。

实现内容：

- 支持 FP16/BF16 输入、FP32 累加以及普通 RMSNorm 和 Add-RMSNorm 两种路径；
- 一次读取 `x` 与 `residual`，同时输出归一化结果和新 residual；
- 针对常见 hidden size 调整 `BLOCK_SIZE`、warps 和向量化加载；
- 与 PyTorch、`torch.compile` 对比数值误差及不同 token 数下的延迟。

推荐原因：实现边界清晰，每个 Decoder Layer 调用两次，适合作为第一个完整算子项目。若端到端收益有限，也应如实分析其受 GEMM 占比限制的原因。

## P2：融合 Q/K Norm + RoPE + KV Cache 写入

这是最推荐的核心亮点。当前 Attention 路径依次执行 Q/K RMSNorm、RoPE 和独立的 KV Cache 写入，Decode 时 batch 较小，容易受到显存访问和 kernel launch 开销影响。

实现内容：

- 为 Decode 编写融合 kernel：读取 Q/K/V，完成 Q/K RMSNorm、RoPE，并按照 `slot_mapping` 将 K/V 写入 Paged KV Cache；
- Q 写入连续输出供 FlashAttention 使用，K/V 直接写 cache；
- 为 Prefill 保留原路径，或单独实现能同时输出连续 K/V 和写 cache 的版本；
- 支持 GQA、不同 head dimension、无效 slot（`-1`）和 CUDA Graph 固定地址。

验收时分别报告融合前后的 kernel 数、显存读写量估算、单层延迟、Decode TPOT 和端到端吞吐。该工作同时展示 Transformer 结构、Paged KV Cache、Triton/CUDA 和推理阶段差异，最适合写入简历。

## 后续阶段安排

P0～P2 原文与阶段编号保留；后续阶段按实施顺序重新规划。**旧 P3「融合采样」暂缓，新 P3 改为输入准备与异步执行，P4 为 KV/Attention 主线，P5 为自适应混合调度。** 下文保留阶段设计，实施状态以各阶段的“当前进度”为准。

| 阶段 | 方向 | 顺序依据 |
| --- | --- | --- |
| P3 | Async ModelRunner：缓冲复用与 CPU/GPU 重叠 | 先完成范围较小的输入准备优化，再验证异步收益与计时方式 |
| P4 | INT8 KV Cache + 融合反量化的 Paged GQA Attention | 延续 P2 的缓存写入路径，作为主要算子亮点 |
| P5 | Decode-aware Mixed Scheduling + 自适应 Prefill Budget | 在执行与缓存接口稳定后，优化在线负载的延迟和吞吐权衡 |

这是实施顺序，不是简历价值排名：P4 是主要算子方向，P3/P5 展示执行与调度能力。以阶段关卡推进，不再预设每项必须在固定周数内完成。

## P3：Async ModelRunner——持久化输入缓冲与 CPU/GPU 重叠

当前进度：P3.1已实现并完成50次端到端对照；P2关闭时decode-heavy吞吐中位数提升1.55%。三次异步关卡的可重叠空间约2%，低于约定5%，本轮不推进P3.2。实现、原始数据位置与适用边界见 [P3验收记录](优化/P3-输入缓冲与异步执行.md)。

当前 `ModelRunner.prepare_decode` 每步构建 Python 列表和 pinned tensor，再搬运到 GPU；采样结果的 `.tolist()` 形成 CPU 等待 GPU 的依赖。先优化输入准备，再决定是否推进完整异步流水线。

### P3.1：拆分测量与持久化缓冲

- 用 Nsight 时间线拆分调度、输入准备、H2D、Graph replay、采样和结果回传，确认 GPU 空闲间隙的来源。
- 预分配并复用 pinned host/device 输入缓冲，减少小张量分配；增量更新 block table、上下文长度和采样参数。
- 保持同步执行语义、现有采样方式和 P2 开关不变，先隔离缓冲复用的收益。
- 测试请求加入/退出、batch 变化、跨 block、Graph padding 和缓冲尾部清理，防止读取上一批遗留数据。

关卡：数值与缓存对照通过，单独报告 CPU 输入准备耗时、分配/搬运次数和端到端结果。若没有明显 GPU 空闲间隙或可隐藏的 CPU 开销，可以先交付缓冲复用，记录原因后进入 P4，不强行重构完整异步调度。

### P3.2：一步前瞻的异步执行

- 先支持 TP=1，让 CPU 准备下一批元数据时 GPU 执行当前批；使用双缓冲和 CUDA Event 管理读写生命周期。
- 处理上一轮 token 的 GPU 侧传递、延迟回填和序列状态更新；不能只删除 `.tolist()` 或增加 `non_blocking=True`。
- 明确 EOS/长度结束、在途请求、Prefix Cache 哈希更新和 KV block 延迟释放的行为，避免提前复用仍被 GPU 使用的资源。
- 保证 Graph 固定地址；host 缓冲复用和设备 Graph 输入覆盖都必须受事件/执行顺序约束，不能仅靠双缓冲假定没有竞态。
- 单卡稳定后再验证 TP=2，各 rank 的调度顺序、事件依赖与退出行为必须一致。Graph bucket 调优仅在 padding/显存数据支持时追加。

当前 `bench.py` 每步 `torch.cuda.synchronize()` 的模式继续作为同步诊断工具；另增异步测量模式，不在每步插入全设备同步。分别记录 GPU 事件时间、用户可见 token 时间及整轮墙钟时间，不能把排队提交时间当作 token 完成时间。

验收：正确性、CUDA Graph 与 TP 冒烟通过；报告 CPU/GPU 重叠、空闲间隙、Decode step 延迟、TPOT 和吞吐。缓冲复用、异步执行及二者叠加分别测量，无收益也保留负结果。

相关模块：`engine/model_runner.py`、`engine/llm_engine.py`、`engine/sequence.py`、必要的调度/块管理逻辑、`bench.py` 和 profiling 工具。

参考 [SGLang 的一步前瞻与 future tokens](https://www.lmsys.org/blog/2024-12-04-sglang-v0-4/) 和 [vLLM ModelRunner V2 的异步设计](https://docs.vllm.ai/en/latest/design/model_runner_v2/)，借鉴依赖管理方法，不直接套用它们的性能数字。

## P4：INT8 KV Cache + 融合反量化的 Paged GQA Attention

当前进度：P4.1～P4.3 及单卡/TP=2、质量、95 次端到端、容量和 Nsight 验收已完成。原 token × head 格式失败后，经确认改为 K32/V per-head；2K/8K 固定子集续写困惑度分别退化 0.324%/0.697%，通过 1% 门槛。高精度 Triton 的 decode-heavy E2E 中位数提升 12.52%；INT8 KV 存储减少 46.09%、同预算槽位增加 85.65%，实际 8K 请求同时准入 21→40，但五组同负载吞吐均回退。默认仍用 Flash/auto，不把容量收益写成提速，详见 [P4 实现与结果](优化/P4-INT8-KV与PagedAttention.md)。

这是后续主要算子方向。P2 已融合 Q/K 预处理与缓存写入，但 Decode Attention 仍调用 FlashAttention。首版面向 RTX 3090、Qwen3-0.6B，优先研究 INT8 存储与 BF16/FP16 计算，不同时引入权重量化。

### P4.1：BF16 Paged Decode Attention 原型

- 从同一 Q、Paged KV Cache、block table 和 context length 出发，对照现有 FlashAttention，先实现正确的在线 softmax 与分块归约。
- 研究 GQA 的 KV 复用和按上下文长度选择分块策略；现有 FlashAttention 已有 split-KV kernel，不能仅以「新增分块」认定收益。
- 覆盖不同 batch、非均匀上下文、head_dim、GQA 比例、非连续输入、无效 slot 和 CUDA Graph；长上下文组合按显存预算减少并发。

关卡：正确性通过，保留多形状延迟、kernel 数和临时显存数据。BF16 原型若慢于 FlashAttention，不切换默认后端；可继续探索 INT8，但必须记录额外计算开销。

### P4.2：INT8 缓存与融合反量化

- 明确 INT8 K/V、scale 的形状和布局，先评估 token × KV head 分组；历史数据的 scale 必须稳定，不能修改 scale 而不重新量化已有数据。
- 在 Attention 内部加载 INT8 并反量化，避免生成完整 BF16 中间缓存；保留 FP32 softmax/归约累加。
- 调整 `allocate_kv_cache` 的容量计算，计入 scale、padding、workspace 和可能的高精度缓冲，不把 payload 减半写成总显存减半。
- 测试跨 block 写入、block 复用、共享前缀引用、scale 生命周期及未命中 slot 不被改写。

### P4.3：集成 P2 与完整缓存生命周期

- 将量化写入接到 P2 融合路径，保留 BF16/INT8 独立选择和不适用配置的显式回退。
- 无缓存前缀的 Prefill 可继续用连续 K/V 做 FlashAttention，同时量化写入；带缓存前缀的 Prefill/chunked prefill 必须增加兼容读取路径，不能把 INT8 Cache 直接传给现有 BF16 接口。
- 暂不支持的场景在引擎/请求选择层明确回退或拒绝，不允许不同路径以不同 dtype/layout 解释同一缓存。完成 Prefix Cache 和 Graph 固定地址验证后，再扩展 TP=2。

验收分三类：同并发、同输入/输出长度下的单层延迟与 E2E/TPOT；相同显存预算下的可缓存 token 数/并发容量；真实文本上的 logits、NLL/困惑度或任务质量变化。以本项目 BF16 路径为正确性与质量参考，不要求随机生成 token 逐个一致，也不新增 Hugging Face 对照要求。

显存容量与延迟实验必须分开：当前分配器会尽量填充显存预算，因此量化后峰值已分配显存未必明显下降。报告实际 bytes/token、scale 开销和容量，区分理论逻辑流量与实际 HBM 流量。若仅有容量收益而无吞吐收益，也如实交付。

相关模块：`layers/attention.py`、新增 Paged Attention kernel、`layers/decode_qkv_fused.py`、`engine/model_runner.py`、块管理与基准工具。

参考 [nano-vLLM KV compression 实践](https://github.com/naalo2/nano-vLLM-kv-compression) 和 [KIVI 的量化分析](https://arxiv.org/abs/2402.02750)。前者包含量化、布局和异步等复合改动；后者的低比特方案也不等同于本项目的 INT8 设计，均不作为预期提速保证。

## P5：Decode-aware Mixed Scheduling + 自适应 Prefill Budget

当前 Scheduler 已有基础 chunked prefill，但一个 step 的 Prefill/Decode 仍互斥；有 Prefill 被调度时会直接返回。此阶段先实现可靠的混合调度，再加入自适应预算控制。

### P5.1：在线负载与指标

- 新增按请求到达时间驱动的负载，覆盖稳定到达、突发请求、长短 prompt 混合及 KV 容量压力；初期直接驱动引擎，无需先实现 HTTP 服务。
- TTFT 从各请求到达开始计时；ITL 记录同一请求相邻输出 token 的可见时间间隔，报告 P50/P99，不能用每请求平均 TPOT 代替 ITL P99。
- 统计队列等待、抢占、重计算 token、KV 使用率、Graph 命中/回退和 P2 融合路径命中。
- 明确定义 TTFT/ITL 延迟目标，报告满足目标的完成请求数/s及其输出 token/s，同时保留总体吞吐与超时比例。

### P5.2：固定预算的混合调度

- 优先调度可运行的 Decode，剩余 token budget 用于 Prefill chunk；总 token 和序列数量都必须受预算约束。
- 将单个 `is_prefill` 标记扩展为能表示分段/混合批次的执行元数据，维护请求顺序与采样位置；中间 Prefill chunk 不生成正式输出。
- Pure Decode 保留 Graph/P2 快速路径；混合批次是否走 Eager、是否绕过 P2、能否使用 P4 的缓存后端，都必须明确并单独测量。
- 增加 KV 准入保护与 Prefill 等待时间保障，防止抢占风暴或 Prefill 长期饥饿。

关卡：CPU 调度/资源管理测试和 GPU 数值对照通过，建立多种固定预算的性能曲线，再开始自适应控制。

### P5.3：自适应预算与公平性

- 根据运行中 Decode 数、实际 Decode 延迟、等待队列和 KV 压力调整 Prefill budget；设置上下限、平滑与滞回，避免逐步振荡。
- 保留 Prefill 最小服务机会和最大等待保护，显式报告 TTFT、ITL 与吞吐之间的取舍。
- 与合理调优的固定预算对照；在相同请求到达轨迹、相同缓存容量下隔离调度收益，再测与 P3/P4 叠加后的效果。

验收：检查无重复/遗漏输出、结束后资源释放、饥饿和抢占边界；报告 ITL P99、真实 TTFT、重计算比例及满足延迟目标的有效吞吐。若收益仅出现在突发或高缓存压力负载中，应注明适用范围。

相关模块：`engine/scheduler.py`、`engine/sequence.py`、`engine/block_manager.py`、`utils/context.py`、模型执行/Attention 入口和在线基准工具。

参考 [nano-vLLM mixed scheduling PR](https://github.com/GeeeekExplorer/nano-vllm/pull/276) 和 [Sarathi-Serve](https://www.usenix.org/conference/osdi24/presentation/agrawal)。基础混合调度已有实践，本项目重点在自适应预算、正确的缓存/执行衔接和可复现的在线对照。

## 验证与结果管理

- 固定当前 P2 提交 `b63fc3e` 为历史锚点；主环境为物理 GPU 1（第二张 RTX 3090）、Qwen3-0.6B，记录 GPU UUID、软件版本、seed、warmup、RMSNorm 后端和全部开关。
- 后续改动默认不启用，保持可独立选择；公平对照需在同一新代码版本切换开关，并固定 P2 是否启用。分别报告单项、逐阶段叠加与必要的组合消融，收益百分比不能直接相加。
- 每组至少重复 5 次，交替原/新运行顺序，报告中位数、波动及原始结果；性能数据来自无 profiler 的运行，profile 用于解释机制。
- 保留旧同步 benchmark，新异步/在线模式单独标记；不同模式的计时定义不能混入同一提升百分比，历史结果无需覆盖。
- P3/P4/P5 的报告分别放在 `docs/优化/`；原始结果按阶段与版本放在 `benchmarks/results/`，分析产物放在 `benchmarks/profiles/`，均继续忽略提交。文档记录命令、配置、关卡与局限性。
- 各阶段结束后都可交付；不以单 kernel 提速替代端到端收益，不预设必须达到某个提升百分比。

## 暂缓与可选方向

- **原 P3 融合采样 / TP logits 通信**：保留候选；只有 profiling 显示采样或通信为瓶颈时再做。当前全词表采样改成 top-k 会改变分布，必须与相同采样语义的参考实现比较。
- **Prefix Cache 淘汰策略**：等待有代表性的重复前缀/会话负载后再评估；必要的缓存命中指标可随 P5 增加。
- **CUDA Graph bucket 优化**：并入 P3 的可选子项，不单独作为已实现亮点。
- **Weight-only Linear、Speculative Decoding、CUDA C++ 重写**：待主线完成或瓶颈证据充分后再启动，不作为 P3～P5 的前置条件。

## 简历呈现方式

保留 P1/P2 的真实成果，后续优先突出 P4 的量化缓存与 Attention 设计，辅以 P3 的执行流水线、P5 的调度策略。每项描述都包含问题、实现、适用配置和已测结果，不提前填写预期收益。

最终 README 应包含架构、复现命令、硬件与软件环境、baseline、消融实验和局限性。即使吞吐收益有限，也可报告经过验证的容量提升、CPU 开销下降或尾延迟改善，并明确质量和公平性的代价。
